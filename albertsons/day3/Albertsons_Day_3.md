<overview>
This is the Markdown reference for the Day 3 lecture deck of Albertsons' "Enterprise AI Architecture Intensive" — a 3.5-day executive/architect training program built and delivered by Dr. Anand Jayaraman (Chief AI Officer, InsightVerge, a Protiviti partner company). The audience is senior IT and business leaders at Albertsons, already through Day 1 (LLM fundamentals, grounding, model right-sizing) and Day 2 (RAG, the policy-engine use case, model selection). Day 3's lecture runs 90 minutes and is followed by a full afternoon of hands-on lab work; the lab (not covered in this deck) has participants build a governed multi-tool orchestrator — six enterprise tool contracts behind a temporary MCP server, routed by a deterministic eligibility table, with human-approval gates and full audit tracing — for a single running scenario: a weekend stockout at "Store 184."

The lecture's job is to give the audience the conceptual and architectural vocabulary the lab will make them build with their hands: what an agent actually is (as distinct from workflow automation), the Model Context Protocol (MCP) as the standardized way an agent discovers and calls enterprise tools, the Agent-to-Agent (A2A) protocol and multi-agent orchestration for when one agent's job gets too big for one context window, and — the section the lab is built entirely around — governance: real, demonstrated exploits, real prompt-injection incidents "in the wild," observability, and the human-approval boundary that no agent is allowed to cross on its own authority.

Structurally the deck has four segments, bookended by an opening bridge from Day 2 and a closing bridge into the lab:
- Opening (slides 1–3): title slide, a roadmap slide, and a bridge slide picking up exactly where Day 2's policy-engine story left off — "the policy says yes, now what?" — establishing that an answer is not an action, and that today's problem is a different kind of system: an agent.
- Segment 1 — What an Agent Actually Is (slides 4–10): agent vs. workflow automation, the brain/memory/tools anatomy, the plan-act-observe-reflect loop, single vs. multi-agent systems, and the closed-enterprise-systems integration problem that MCP exists to solve. Includes a live-demo bridge slide ("Watch It Decide") cueing the instructor's first n8n demo: a single agent with a calculator tool and a Tavily search tool, asked the price of 13 grams of 22-carat gold in Bangalore, so the room can watch it dynamically decide which tool to use and how many times.
- Segment 2 — MCP: Giving It Hands (slides 11–19): APIs vs. MCP, a "tools hardcoded" CrewAI code example as the old-world contrast, the four-box MCP architecture (LLM / Agent Code / MCP Client / MCP Server), a running Zerodha trading-agent example ("should I buy more HDFC Bank today?") walked through its three MCP phases — capability discovery, resource fetch, tool invocation — then the ReAct (Reasoning + Acting) loop that ties those phases together, and a slide honestly counting how many LLM calls that one question actually costs.
- Segment 3 — A2A: Giving It Colleagues (slides 20–27): the moment one agent's job outgrows one context window ("rebalance my entire portfolio for a market downturn"), the A2A protocol and a four-specialist supervisor architecture (Research / Risk & Tax / Compliance / Execution agents), a step-by-step trace of that rebalancing scenario, a clean side-by-side of MCP vs. A2A, a "digital departments" enterprise vision slide, the three orchestration patterns (sequential/parallel/hierarchical), a framework comparison table (LangGraph, CrewAI, n8n, Microsoft Agent Framework), and a second live-demo bridge slide ("Watch Them Coordinate") cueing the instructor's multi-agent n8n demo: a Finance Agent, News Agent, and Risk Agent feeding a "CIA Agent" that writes a report and sends an email.
- Segment 4 — Governance, Observability & Risk (slides 28–31): why governance isn't optional (four named failure modes), a real documented exploit against a real expense-approval system (the same $2,500 no-receipt rule, defeated by one contextual reframing), two real screenshots of prompt injection being used in the wild (a job application, a court filing), and an observability/debugging slide comparing LangSmith, LangFuse, and Azure Application Insights (the last of which the afternoon lab actually instruments with).
- Closing (slide 32): explicitly hands off to the lab — "your lab runs the mechanism we theorized" — and previews what to watch for there (the governed-orchestrator boundary, the human-approval trigger, how to keep score like an architect).

<slide number="13">
Text content: Eyebrow: "SEGMENT 2 • MCP: GIVING IT HANDS". Title: "What MCP Is — The Architecture". Four-box chain: LLM (text in, text out, stateless) → Agent Code (orchestration loop, reads output, calls MCP) → MCP Client (library inside your agent) → MCP Server (Tools · Resources · Prompts · Auth). Two callouts: "MCP never talks to the LLM directly" (agent code fetches capabilities and injects them into the prompt before every call; the LLM only ever sees text); "The MCP connection IS stateful" (the server holds session context between calls — fetch portfolio, check margin, place order, all one session).
Image context: None (four-box architecture chain with bidirectional arrows).
<notes></notes>
<narration>Two things people consistently get wrong about MCP, so let's nail them here. First: MCP never talks to the LLM directly — the LLM only ever sees plain text, and it's your agent code's job to fetch capabilities and weave them into the prompt. Second: the connection itself is stateful, even though the LLM is stateless — the server can hold session context across a whole sequence of calls. Keep both of those straight and the rest of this segment will make a lot more sense. Let's make it concrete with one running example.</narration>
</slide>

<slide number="18">
Text content: Eyebrow: "SEGMENT 2 • MCP: GIVING IT HANDS". Title: "The ReAct Loop — How the Agent Actually Thinks". Body: "ReAct = Reasoning + Acting. Every agentic framework you'll touch today runs this pattern underneath." Three-box loop: THINK (LLM is called, reads history, decides next action — "LLM's job") → ACT (agent code runs, calls MCP server, fetches or invokes — "Agent code's job") → OBSERVE (result appended to history, LLM sees this next call — "Memory mechanism"), looping back to THINK. Exit condition: "when THINK produces a final answer instead of an action → return to user." Caption: "Zerodha trace: Think → fetch portfolio | Think → fetch market data | Think → fetch margin | Think → recommend order | Think → done. Roughly 4–5 LLM calls for one question."
Image context: None (three-box loop diagram with a labeled return arrow and an exit condition).
<notes></notes>
<narration>ReAct — reasoning and acting, interleaved. Think, act, observe, and back to think, until the model decides it has enough to give a final answer instead of taking another action. Trace it through our Zerodha example and you get five distinct "think" steps for one question — fetch portfolio, fetch market data, fetch margin, recommend the order, then done. That's roughly five separate LLM calls to answer "should I buy more HDFC Bank today?" Which raises an honest question worth asking out loud: is that a good number, or a wasteful one?</narration>
</slide>

Save the dynamic, re-decide-every-time behavior for the part that genuinely depends on what the data says: the action phase. That one design choice alone saves two to three LLM calls per query, and at enterprise scale, that's real latency and real cost. That's MCP and the ReAct loop, end to end.
